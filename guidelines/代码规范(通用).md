# 通用代码规范 (Universal Coding Standards)

**版本**: 2.2.0  **日期**: 2026-10-15  **类型**: 多语言通用基准规范

> **行为规范继承**：AI 编码助手在执行本规范代码任务时，**必须严格遵循 [AI行为规范.md](./AI行为规范.md)**（含 5 阶执行模型、最小变更、计划先行与高强度验证）。
> **适用范围**：所有编程语言（Python, JavaScript, TypeScript, Go, Java, Rust, C# 等）的新代码；修改老代码遵循最小变更原则。
> **语言专用覆盖**：C++ 项目优先遵循《代码规范(C:C++)》，UE5 项目优先遵循《代码规范(C++UE5)》；两者冲突时以具体语言/引擎规范为准。
> **优先级（高→低）**：[AI行为规范](./AI行为规范.md) > 安全与正确性（4, 6）> 可读性与架构（2, 3）> 性能与风格（1, 8）。

## 1. 代码风格与格式化统一

### 1.1 团队与语言官方惯例
- **必须**严格遵循目标语言官方或行业事实标准风格指南（如 Python PEP 8、Go gofmt、Java Google Java Style、TypeScript ESLint Standard）。
- **必须**优先遵循目标仓库既有的格式约定；同一项目内**严禁**混用 Tab 和空格缩进。

### 1.2 编码与换行
- 源码文件**必须**使用 UTF-8 无 BOM 编码。
- 源码文件**必须**使用 LF（`\n`）换行符，**严禁**在任何平台下使用 CRLF。

### 1.3 注释规范与函数内部零注释原则
- **核心铁律：禁止在函数体内添加任何业务解释性行内或块注释**。
- 函数实现思路、关键步骤、核心算法与注意事项，**必须**集中写在函数定义上方的文档注释块中（如 Python `"""docstring"""`、TypeScript/Java `/** */`、Go `//` 文档注释）。
- **唯一例外**：允许且仅允许静态分析/编译器指令（如 `# type: ignore`、`// NOLINT`、`// eslint-disable-next-line`、`/* fallthrough */`）。
- 若函数内部过于复杂必须依赖解释性注释才能被看懂，说明严重违反单一职责，**必须直接拆分为更小粒度的子函数**。

**正例 (Python)**：
```python
def calc_score(user: UserData) -> int:
    """计算用户综合得分。

    实现思路：基础分 + 活跃度加成 - 违规扣分。
    """
    bonus = user.active_days * BONUS_PER_DAY
    return user.base_score + bonus - user.violations * PENALTY
```

**反例 (Python)**：
```python
def calc_score(user: UserData) -> int:
    bonus = user.active_days * BONUS_PER_DAY  # 计算活跃天数加成（错！禁止行内注释）
    return user.base_score + bonus - user.violations * PENALTY  # 返回得分（错！）
```

## 2. 命名与语义规范

> **项目优先原则**：进入已有代码库时，AI **必须**先推断既有命名的风格（蛇形 snake_case、小驼峰 camelCase、大驼峰 PascalCase），保持风格统一；新项目未明确约定时必须向用户询问。

### 2.1 语义直观性
- 变量、函数、类名**必须**具备直观的业务与技术语义，自解释其职责，**禁止**无意义的单个字母（循环索引 `i`/`j` 除外）或难以辨认的缩写。
- 常量**必须**具备清晰的视觉识别度（通常全大写加下划线：`MAX_RETRY_COUNT`）。

### 2.2 内部与私有成员隔离
- 对缺乏原生访问控制的语言（如 Python），私有属性/方法**必须**使用单下划线 `_` 前缀显式标明内部属性。
- **禁止**使用双下划线 `__` 前缀（在 C++ 等底层语言中属保留标识符；在 Python 中会触发 name mangling 破坏多态访问）。

## 3. 架构设计与工程七大守则

所有工程设计与功能实现**必须**严格遵循以下七大核心原则：
1. **单一职责 (SRP)**：每个类、模块或函数只做一件事，**禁止**编写几百行的多功能巨型函数。
2. **开闭原则 (OCP)**：代码结构对扩展开放，对修改关闭；通过扩展而非修改已有核心代码来实现新需求。
3. **里氏替换 (LSP)**：子类或派生实现必须能完全替换其基类或接口，保持行为一致。
4. **依赖倒置 (DIP)**：高层业务逻辑必须依赖抽象接口，而非直接依赖具体底层实现。
5. **接口隔离 (ISP)**：保持接口精简聚焦，**禁止**强迫调用方依赖它们不需要的方法。
6. **DRY 原则 (Don't Repeat Yourself)**：**严禁**复制粘贴逻辑，公共代码必须收敛复用。
7. **KISS 原则 (Keep It Simple, Stupid)**：保持代码简单直接，**禁止**过度设计和无谓的过早泛化。

## 4. 健壮性与错误处理

### 4.1 强类型与类型标注
- 在支持类型系统的语言（TypeScript、Python、Go、Java、Rust）中，**必须**为所有公共函数形参、返回值及结构体成员提供明确的类型标注。
- **严禁**在 TypeScript 中滥用 `any`（应使用 `unknown` 并收缩类型，或定义清晰的 `interface`）。
- **严禁**在 Python 3 中忽略 `typing` 类型标注。

### 4.2 精确异常与资源安全释放
- **严禁裸捕获异常**（如空 `catch {}` 或空 `except:` 默默吞掉错误）。
- **禁止捕获过宽基类异常**（如 `catch (Exception e)` / `except Exception:`），**必须**精确捕获预期的具体异常类型；仅在系统最外层网关或进程守护处方可统一记录并优雅降级。
- 持有的外部资源（文件句柄、网络套接字、数据库连接、锁）**必须确保 100% 释放**，优先使用各语言的 RAII、`try-with-resources` (Java)、`defer` (Go)、`using` (C#) 或上下文管理器 `with` (Python)。

### 4.3 异步与并发安全
- **严禁出现未处理的 Floating Promise / 悬空协程**：所有异步调用必须有明确的 `await`、`.catch()` 链式处理或结构化取消机制。
- 跨线程/协程共享可变数据时，**必须**使用并发安全的同步原语（互斥锁、Channel、原子操作），严禁在无同步机制下进行竞态读写。

**正例 (TypeScript)**：
```typescript
try {
    await fetch_user_data(user_id);
} catch (error: unknown) {
    if (error instanceof NetworkTimeoutError) {
        logger.warn("network timeout, retrying...", { user_id });
        return fallback_user_data;
    }
    throw error;
}
```

**反例 (TypeScript)**：
```typescript
try {
    fetch_user_data(user_id);  // 错！未 await，成为悬空 Floating Promise
} catch (e) {                  // 错！捕获不到未等待的 Promise 异常
    // 空处理（错！吞掉错误）
}
```

## 5. 工程化、依赖与供应链安全

### 5.1 自动化工具链与 Linter
- 项目**必须**配置 Lint 静态检查与格式化工具（Prettier, ESLint, Black, Ruff, golangci-lint 等）。
- 提交前必须通过自动化格式化与静态检查校验。

### 5.2 依赖管理与可复现构建
- **严禁**擅自引入未在项目中报备或过重的不必要第三方依赖，优先使用标准库。
- **必须**提交并维护 lockfile（`package-lock.json`, `pnpm-lock.yaml`, `Cargo.lock`, `go.sum`, `poetry.lock`），确保团队构建 100% 可复现。
- **禁止**在依赖声明中使用 `latest` 标签或通配符 `*`。
- **必须**遵守开源协议合规性，商业专有项目中**严禁**混入具有强传染性的 GPL 源码。

## 6. 可观测性与安全规范

### 6.1 结构化日志
- **必须**使用统一日志框架，按业务影响准确使用级别（`DEBUG`, `INFO`, `WARN`, `ERROR`, `FATAL`）。
- 关键业务主链路必须包含跟踪 ID（Trace ID），支持链路透传与可追溯性。

### 6.2 凭据与敏感数据保护
- 日志、源码、配置文件、单测中，**严禁**硬编码密钥、密码、API Token、私钥或未脱敏的用户个人隐私数据。

### 6.3 注入防御
- 数据库操作**必须**使用参数化查询（Prepared Statements）或 ORM 绑定机制，**严禁直接用字符串拼接 SQL**。
- 动态表名/列名必须使用白名单校验，严禁透传用户输入。

### 6.4 12-Factor 配置管理
- 应用配置**必须**从环境变量或外部配置中心读取，严禁硬编码。
- `.env` 本地私密配置文件**必须**加入 `.gitignore`，代码库中仅提供 `.env.example` 占位模板。
- 应用启动时**必须**对必填配置执行强校验，若配置缺失必须快速失败并输出清晰指引。

## 7. 测试规范

- **单测覆盖与可复现性**：新功能与核心逻辑重构**必须**配套单元测试，测试用例必须覆盖正常路径、边界值与错误路径。
- **严禁在测试中 sleep 盲等**：测试异步逻辑时，**禁止使用硬编码的 `sleep(3000)`**，必须使用事件回调、轮询检查（带超时上限）或虚拟时钟（Mock Timers）。

## 8. 控制流与代码简洁原则

### 8.1 提前返回 (Guard Clause)
- 函数主逻辑**必须**保持线性一路向下，禁止深层嵌套：

**正例**：
```python
def process_order(order: Order) -> bool:
    if not order.is_valid:
        return False
    if order.is_cancelled:
        return False
    return execute_payment(order)
```

**反例**：
```python
def process_order(order: Order) -> bool:
    if order.is_valid:
        if not order.is_cancelled:  # 嵌套右移
            return execute_payment(order)
    return False
```

### 8.2 必要防御原则与杜绝过度防御（Like Human Engineers）
- **核心铁律：非确定不判断就会出错，绝不添加判断**。
  - AI **必须像资深人类工程师一样思考与编码**，只在真正的关键边界（系统外部不可信输入、或接口显式契约声明可能返回空/失败态）做必要校验。
  - **严禁过度防御（神经过敏）**：绝不能因为某个地方出错的几率只有 0.1% 甚至 0% 就去写一个防御分支；**严禁**为不存在或概率极低的臆想场景层层设卡。
- **防御边界划分准则**：
  - **外部不可信边界（必须校验）**：HTTP/RPC 入参、未校验的文件或用户输入、Public 导出 SDK API。
  - **内部受信任链路（信任契约）**：类内部不变式、强类型系统保证、已由前置中间件/拦截器保证的数据。严禁在内部可信路径重复判空。

**正例 (Python - 像人类工程师一样聚焦关键业务边界)**：
```python
def process_user_payment(order: Order, wallet: Wallet) -> bool:
    """处理用户支付扣款。仅校验余额不足这一真实业务边界。"""
    if wallet.balance < order.total_amount:
        return False
    wallet.deduct(order.total_amount)
    return True
```

**反例 (Python - AI 典型的神经过敏过度防御)**：
```python
def process_user_payment(order: Order, wallet: Wallet) -> bool:
    if order is None: return False              # 错！内部上游已保证非空
    if wallet is None: return False             # 错！类型标注与上游已保证非空
    if order.total_amount is None: return False  # 错！模型字段不变量已保证
    if order.total_amount < 0: return False      # 错！订单创建时已校验金额合法
    if wallet.user_id != order.user_id:          # 错！已由权限中间件校验，此处纯属臆想防御
        return False

    if wallet.balance < order.total_amount:
        return False
    wallet.deduct(order.total_amount)
    return True
```

## 附录 B：通用代码审查高频陷阱

| 检查项 | 违规表现 | 正确做法 |
|---|---|---|
| **注释滥用** | 在函数内部随处打 `// 赋值给 x` | 删掉内部行内注释，将思路写在函数头部文档中 |
| **类型逃逸** | TypeScript 遇到复杂对象直接标 `any` | 定义清晰的 `interface` 或使用 `unknown` + 类型保护 |
| **错误吞没** | `catch (e) {}` 里面什么都不做 | 捕获具体类型，记录包含上下文的日志并处理/重新抛出 |
| **异步悬挂** | 直接调用异步函数而不 `await` | 必须显式 `await` 或接入结构化 Promise 错误链条 |
| **依赖失控** | `package.json` 写入 `"lodash": "*"` | 使用明确兼容版本并提交 `lockfile` |
| **安全红线** | 代码里写死了 `apiKey = "sk-..."` | 迁移到环境变量或秘密管理器中动态注入 |
| **控制流** | 4 层 `if-else` 嵌套包着核心业务 | 使用 Guard Clause 提前返回，拉平主干逻辑 |
| **过度防御** | 每一个调用子函数都再判一次入参是否为 null，为 0.1% 极小概率设卡 | 坚持必要防御原则，非确定不判断就会出错绝不添加判断，内部遵循契约 |
