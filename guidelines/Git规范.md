## 1. 提交权限与执行铁律

- **严禁擅自提交（Explicit User Trigger Only）**：
  - Git 提交是项目历史的正式固化动作，**必须经由用户显式指令（如明确说“提交”、“commit”）方可执行**。
  - 用户未明确要求提交前，**严禁自行执行 `git commit` 或 `git push`**。
  - 未获提交指令时，AI 的职责是在工作区保留修改并向用户汇报改动摘要，等待用户审查确认后由用户决定何时提交。

---

## 2. 提交信息格式契约

Git 提交信息**必须**采用结构化格式：

```
[类型]: 简短概述本次变更的核心目的
- 具体改动点1（说明改了什么以及为什么改）
- 具体改动点2
...
```

- **允许类型标签**：
  - `feat`: 新增功能、规范或模块
  - `fix`: 缺陷修复、规则修正
  - `docs`: 纯文档更新与排版微调
  - `style`: 代码排版（不改变逻辑的格式变动）
  - `refactor`: 重构（非新增功能且非修复缺陷的代码重组）
  - `test`: 增加或更新测试用例
  - `chore`: 构建过程、依赖或辅助工具变动
- **格式要求**：
  - 首行简短描述必须精炼概括核心目的，字数建议控制在 50 字以内。
  - 变更描述必须使用 `- ` 无序列表详细说明“改了什么”及“为什么改”。

## 3. 分支管理与命名模型

- **分支命名格式**：`类型/功能或问题简述`（全小写，短横线分隔）。
  - 特性开发：`feat/user-auth`, `feat/inventory-replication`
  - 缺陷修复：`fix/null-pointer-crash`, `fix/login-timeout`
  - 架构重构：`refactor/interface-first-layout`
- **保护主分支**：`main` / `master` 分支保持随时可发布状态，禁止在无审查情况下直接推送未经测试的破坏性改动。

---

## 4. 语义化版本规则 (SemVer)

规范文件、基础库与发布模块严格遵循 `主版本.次版本.修订号`（Major.Minor.Patch）：
- **主版本号 (Major)**：发生重大架构变动、不兼容规则重构或破坏性 API 变更时递增。
- **次版本号 (Minor)**：新增章节、新增非破坏性规则、新增向后兼容特性时递增。
- **修订号 (Patch)**：修复文字笔误、修正已有规则描述、修复格式排版或补充正反例时递增。
- **严禁只改内容不改版本号**：任何修改涉及带版本号的规范或模块，必须同步提升版本号并追加版本履历。

## 5. 仓库过滤与大文件资产协同 (LFS)

### 5.1 忽略规则 (.gitignore)
- **严禁提交编译产物与临时文件**：包括但不限于二进制输出、IDE 配置（如 `.idea/`, `.vscode/` 除受版本管理的配置外）、系统临时文件（`.DS_Store`）。
- **UE5 引擎工程必须过滤**：`Binaries/`, `Intermediate/`, `Saved/`, `DerivedDataCache/`。
- **配置防护**：禁止随意提交 `.uproject` 中的 `Plugins` 数组变更（除非明确新增/删除了插件）。

### 5.2 大文件存储 (Git LFS)
- 二进制资产、多媒体资产（如 UE5 的 `.uasset`, `.umap`, 纹理, 音效等）**必须**在 `.gitattributes` 中配置并通过 Git LFS 管理，严禁直接检入普通 Git 存储库膨胀体积。
