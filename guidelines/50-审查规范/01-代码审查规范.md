## 一、 五阶审查执行流水线 (Five-Step Review Pipeline)

AI 审查员在执行代码审查时，**必须严格按照以下先后顺序分步推进，严禁跳步或颠倒次序**：

```
Step 1: Bug与真实缺陷排查 ──► Step 2: 全体系规范合规核验 ──► Step 3: 优化空间评估与方案输出 ──► Step 4: 回归审查与完工判定 ──► Step 5: 人工裁决门禁
   (极端条件不算缺陷)          (过度防御/注释/测试等)          (先实现后优化/保结果一致)        (确证零副作用与无残留)       (由人类决定是否采纳)
```

### Step 1: 真实 Bug 与业务缺陷排查 (Defect & Logic Scan)
- **核心任务**：首先审查代码中是否存在直接导致功能损坏、逻辑断裂、死锁、并发竞态、内存泄漏、悬垂引用或未处理故障流的**真实 Bug 与缺陷**。
- **安全与性能缺陷**：越权、注入、SSRF、明文凭据、不安全反序列化，以及可证实的 N+1、死锁、热路径阻塞或高频日志，按真实缺陷处理；无法量化的性能优化建议只能作为优化项，不得冒充 BLOCKER。
- **一票免除红线（极端条件不算缺陷）**：
  - **信契约弃臆想**：基本不可能出现的极端条件（如 0.1% 极小概率硬件级异常、上游类型系统或前置守卫已 100% 保证的不变量），**绝对不能作为 Bug 或缺陷提出**。
  - **严禁借找茬之名强推过度防御**：严禁无视调用方契约，对已保证非空的对象要求层层判空。

### Step 2: 规范合规性审查 (Standards Compliance Review)
在确认主干业务逻辑无真实 Bug 后，逐项核验全体系规范一票否决项：
1. **过度防御 (B4)**：是否存在针对内部可信链路的层层设卡、多余判空或臆想防御？
2. **注释纯粹性与 100% 同步 (B-CMT)**：
   - 函数体内是否绝对零业务行内注释（仅放行静态分析指令）？
   - 函数文档头是否为语言原生的多行文档格式（C++/UE5 为分标签 Doxygen：`/**` 与 `*/` 独占行、`@brief` 必填、参数/返回值逐项成行；Python 为 Docstring；TS 为 JSDoc；严禁单行压缩）？
   - 修改或修复代码后，文档头注释与各标签是否已 100% 真实对齐最新实现？
3. **真实测试与 95% 覆盖率 (B5)**：
   - 核心业务模块、接口契约与关键组件的行覆盖率与分支覆盖率是否达到 **$\ge 95\%$**（脚手架/生成代码/平台适配经人工审批可豁免）？
   - 是否存在空跑无断言、空洞断言、吞异常、核心逻辑全量 Mock 同义反复、sleep 盲等**滥竽充数**测试代码？
4. **架构与职责边界 (R-ARCH-CLASS)**：是否遵循单文件单类？UI 层是否越权修改业务数据或持久化？
5. **专有语言陷阱**：C++ 15 层排布/防 NRVO 破坏/RAII；UE5 UPROPERTY/命名/GC 防御；机密脱敏等。
6. **应用安全 (R-SEC-*)**：认证授权是否服务端强制执行？对象级/租户级归属是否校验？输入输出、CSRF/SSRF、加密与凭据、反序列化、限流是否合规？（见 [10/08 应用安全](../10-通用代码规范/08-应用安全规范.md)）
7. **性能与资源**：是否存在可证实的 N+1、无界查询、热路径锁竞争/日志/分配、无界缓存或内存增长？性能结论是否有 profile/benchmark 证据？（合格证据最小集见 [10/03 §5.5](../10-通用代码规范/03-测试控制流与速查.md#55-证据最小集)）
8. **依赖与供应链**：新增依赖是否有明确必要性与许可证/漏洞/维护性评估？Lockfile 是否同步？是否存在未审计的传递依赖？

### Step 3: 可优化空间评估与方案产出 (Optimization Potential & Proposal)
在功能正确且规范达标的前提下，全面审视所有代码是否存在进一步优化空间（算法性能、内存开销、认知复杂度、SLAP 单一抽象层次、意图变量解构等）：
- **核心铁律（先实现，后优化）**：严禁在基本功能未稳定通过前过早优化。
- **性能结论必须有证据**：涉及性能优化的结论必须附 profile/benchmark 或可复现度量，禁止凭感觉优化；证据须含环境与基线对照（见 [10/03 §5.5](../10-通用代码规范/03-测试控制流与速查.md#55-证据最小集)）。
- **等价性铁律（保证结果绝对一致）**：优化方案必须选用业界最佳实践，且**必须 100% 保证外部接口契约、运行时业务行为及所有测试结果与原实现完全一致（Zero Semantic Regression）**。
- **输出要求**：若存在优化空间，必须输出一份独立的《代码优化建议方案》（包含：现状瓶颈、最优优化方案、重构 Diff 预览、收益预测与等价性保证）。

### Step 4: 回归审查与完工判定 (Regression Verification & Sign-Off)
若本轮审查中修正了任何 Bug 或实施了优化：
- **回归核验**：审查确认改动是否引入了任何新的副作用、逻辑退化或编译警告；
- **测试核验**：全量自动化回归测试必须全绿，核心业务覆盖率保持 $\ge 95\%$（豁免须人工审批）；
- **完工准出**：若已无任何 Bug 与规范问题，且回归核验确证零缺陷，方可判定代码“技术审查完成（Review Passed）”。

### Step 5: 人工裁决门禁 (Human-in-the-Loop Decision Gate)
- **人工决策特权**：Step 3 产出的优化方案，**必须交由人类工程师人工审查并最终裁决**是否进行优化处理。
- **严禁擅自实施**：未获得人类明确批准指令前，AI 严禁擅自执行侵入性的重构与优化（触及范围内确证无害的死代码清理与等价合并特权除外）。

## 二、 审查维度与阻断分级 (Veto & Severity Criteria)

审查代码变更（Git Diff）时，按下表判定；涉及安全、正确性、数据损坏与一票否决项的直接阻断，性能/认知负荷等可修复项按严重度分级处理：

| 审查维度 | 违规判定标准 (按严重度分级) | 允许放行特权与豁免标准 |
|---|---|---|
| **1. 业务逻辑与缺陷** | 存在真实功能失效、数据损坏、竞态条件、死锁、内存泄露或未捕获的真实异常 | 极端条件与 0.1% 极小概率虚构场景**不计为缺陷**，内部可信契约信任放行 |
| **2. 过度防御 (B4)** | 内部受信任链路层层设卡；为极小概率虚构防御；判断引用非空（`&ref == nullptr`）或判断 `this == nullptr` | 仅外部不可信边界（HTTP/RPC/未校验文件/Public SDK API）设防 |
| **3. 注释纯粹性与同步 (B-CMT)**| 函数体内出现业务解释行内/块注释；C++/UE5 文档头写成单行压缩 `/** @brief ... */` 或缺失标签；Python/TS 缺少多行 Docstring/JSDoc；**修改代码后未同步刷新函数文档头，或注释与真实实现脱节不一致** | 仅放行静态分析指令（`// NOLINT`、`# type: ignore`）；文档头为语言原生多行格式且与实现 100% 对齐 |
| **4. 变更边界 (B3)** | 顺手修改无关代码；大面积擅自重排版或重命名未触及符号 | 触及范围内确证 100% 无副作用的未引用变量删除、死代码清理与等价合并 |
| **5. 真实测试 (B5)** | 核心业务模块测试行或分支覆盖率未达 95%；出现空跑无断言、空洞断言（如仅 `assertNotNull`）、吞异常、核心逻辑全量 Mock 同义反复等滥竽充数测试；测试使用 sleep 盲等；破坏私有封装 | 核心业务真实测试覆盖率达到 95% 以上（豁免须人工审批）；真实内存对象测核心逻辑；精确断言具体业务值、状态转移与确切异常类型 |
| **6. 缺陷根治 (B7)** | 报错点就地判空/吞异常掩盖根因；修 Bug 漏测上下游契约与全景同类排查 (Pattern Sweep) | 锁定破坏不变式的源头；完成三向测距并排查镜像实现 |
| **7. 语言专有陷阱** | **C++**: `return std::move(p)` 阻断 NRVO；返回临时对象 view；漏标 `override`/`noexcept`；非 15 层排布<br>**UE5**: 漏标 UPROPERTY 遭 GC 误杀；非大驼峰或带 `_t`；非 GameThread 摸 UObject | 严格遵循 C++ 与 UE5 专有规范约束 |
| **8. 工具安全 (B-SEC)** | 代码/日志明文泄露 Key/Token；私装未授权依赖；遗留排查调试临时脚本 | 凭据绝对脱敏掩码；依赖锁版本；工作区绝对洁净 |
| **9. 认知负荷控制** | 复合长表达式未提取意图变量；嵌套三元；缩进深度 > 3 层；裸布尔 Flag 参数控制耦合；散落未命名魔数；反向否定布尔命名 | 落实具名意图常量、正向布尔命名、SLAP 单一抽象层次与具名枚举 |
| **10. 职责边界与文件组织 (R-ARCH-CLASS)** | 一个文件堆叠多个业务类；嵌套无关业务类或借嵌套规避单文件单类；UI 类直接修改业务数据或持久化；上帝类跨层越权 | 单文件单类（纯类型聚合头文件除外）；嵌套类为内部实现细节；UI 仅展示与派发意图，数据变更经服务/命令层 |
| **11. 应用安全 (R-SEC-*)** | 服务端缺失认证/授权；对象级或租户级越权；输入未校验；输出未编码；CSRF/SSRF 防护缺失；弱哈希/硬编码密钥；不安全反序列化；敏感接口无限流 | 服务端强制鉴权与默认拒绝；边界 allowlist 校验；上下文编码；强哈希与密钥管理；敏感接口限流与幂等 |
| **12. 性能与资源** | 可证实的 N+1/无界查询；热路径锁竞争、同步 I/O、高频日志或无界分配；无界缓存/队列导致内存增长；性能结论无 profile/benchmark 证据或无环境/基线对照 | 有量化证据的优化；保持外部行为等价；不做过早优化 |
| **13. 依赖与供应链** | 新增依赖无必要性/许可证/漏洞评估；Lockfile 未同步；使用浮动版本；引入未审计传递依赖 | 依赖锁版本；CVE/许可证/SBOM 审核；新增依赖经评审 |

> **默认严重度**：第 1–8、10–11、13 项为 **BLOCKER**；第 9、12 项为 **MAJOR**（若已造成数据损坏、线上故障或安全事件，升级为 BLOCKER）。完整分级与合并策略见 §三。

## 三、 审查严重度与 PR 拆分门禁

### 3.1 问题严重度
| 级别 | 判定标准 | 合并策略 |
|---|---|---|
| **BLOCKER** | 功能错误、数据损坏、安全漏洞、覆盖率/测试门禁未达标、违反 B-CMT/B3/B7 等一票否决项 | 必须修复并回归通过后方可合并 |
| **MAJOR** | 可证实的性能/资源风险、缺少关键边界测试、明显可维护性隐患 | 修复或由人类书面豁免并登记技术债 |
| **MINOR** | 命名、结构、可读性等非功能问题 | 可本轮修复或转后续任务 |
| **NIT** | 个人偏好、可选优化 | 不阻断合并 |

### 3.2 PR 拆分门禁
- 单个 PR/MR 建议控制在 **≤ 400 行有效变更**；超过时优先拆分。
- 跨 **≥ 3 个模块**，或同时混合“功能 + 重构 + 格式化/重命名”时，必须拆分或提供书面说明。
- 机械重命名/格式化必须独立提交，禁止与业务变更混在同一 Diff。
- 生成代码、第三方 vendor、批量迁移可豁免行数限制，但必须在审查说明中标注。

## 四、 标准审查报告输出模板

AI 审查员在输出审查意见时，**必须严格遵循以下结构化格式**（对应 [templates/CODE_REVIEW_TEMPLATE.md](../templates/CODE_REVIEW_TEMPLATE.md)）：

```markdown
## 📋 代码审查报告 (Code Review Summary)

### 1. 评审总判定 (Review Verdict)
- **综合结论**: [ PASS (准予合并) | NEEDS_WORK (需整改) | REJECT (严重否决) ]
- **问题分级**: BLOCKER [n] / MAJOR [n] / MINOR [n] / NIT [n]
- **核心评价**: 一两句话概括本次提交的代码质量与关键问题。

### 2. Step 1: Bug 与真实缺陷清单 (Defects & Logic Issues)
> 注：仅记录影响功能与稳定性的真实缺陷；极端条件与极小概率场景不计为缺陷。
- **[BLOCKER] 严重缺陷**: `path/to/file.cc:42` - 问题说明与修复方案。
- *(若无缺陷则注明：未发现真实业务缺陷与逻辑漏洞)*

### 3. Step 2: 规范合规核验结果 (Standards Compliance)
- **过度防御 (B4)**: [ PASS / FAIL - 说明 ]
- **注释纯粹与 100% 同步 (B-CMT)**: [ PASS / FAIL - 是否为语言原生多行文档格式且与最新实现忠实对齐 ]
- **真实测试与 95% 覆盖率 (B5)**: [ PASS / FAIL - 核心业务行/分支覆盖率及是否存在滥竽充数测试 ]
- **职责边界 (R-ARCH-CLASS)**: [ PASS / FAIL - 单文件单类及跨层规范 ]
- **语言专有红线**: [ PASS / FAIL ]
- **应用安全 (R-SEC-*)**: [ PASS / FAIL - 认证授权/输入输出/CSRF/SSRF/加密/反序列化/限流 ]
- **性能与资源**: [ PASS / FAIL - 是否存在可证实 N+1/热路径问题及 profile 证据 ]
- **依赖与供应链**: [ PASS / FAIL - 新增依赖/Lockfile/CVE/许可证 ]

### 4. Step 3: 代码优化建议方案 (待人工审查裁决)
> 注：先确保功能正确再进行优化；优化方案必须保证业务结果与既有行为 100% 一致。
- **是否存在优化空间**: [ 是 / 否 ]
- **优化点描述**: （如算法时间复杂度、内存分配热点、认知复杂度降低等）
- **推荐优化方案与 Diff 预览**:
  ```diff
  - [当前实现]
  + [最优优化实现]
  ```
- **等价性与收益保证**: 说明为何优化后行为 100% 一致及具体收益。
- **人工决策提示**: ⚠️ 本优化方案已就绪，等待人工审查裁决；未获明确授权前暂不应用。

### 5. Step 4: 回归审查与完工判定 (Regression & Sign-Off)
- **回归验证状态**: [ 验证通过，无副作用退化 / 待回归 ]
- **完工判定**: [ 技术准出就绪，等待人工确认 / 阻断待修 ]
```

## 五、 AI 审查员系统提示词模板 (System Prompt)

可直接将以下文本注入至 AI 工具中，使 AI 严格按五阶流水线执行审查：

```markdown
你是一名极其严谨的资深架构师与代码审查专家。请遵循《AI 代码审查规范》对提交的代码变更进行审查。

你的审查必须严格遵循以下五阶流程：
1. 【先查 Bug 与真实缺陷】：仅识别功能失效、逻辑断裂、死锁、并发竞态、内存泄漏等真实缺陷。牢记：极端条件或 0.1% 极小概率的虚构问题不算缺陷，信契约弃臆想，严禁借找茬推行过度防御。
2. 【再查规范合规性】：逐一核验过度防御(B4)、注释纯粹性与100%同步更新(B-CMT，按语言原生多行文档格式)、核心业务测试覆盖率>=95%且零滥竽充数测试(B5)、单文件单类与职责边界(R-ARCH-CLASS)、语言专有陷阱、应用安全(R-SEC-*)、性能与资源、依赖与供应链等一票否决项。
3. 【评估优化空间并出方案】：在功能正确和规范达标前提下，审视是否有性能、内存或可读性优化空间。遵循“先实现后优化，保结果一致”原则，提出业界最佳优化方案并提供 Diff 与等价性保证。
4. 【回归审查与完工判定】：确证修改无任何副作用退化，自动化回归测试全绿，方可给出技术完工判定。
5. 【人工决策门禁】：按 BLOCKER/MAJOR/MINOR/NIT 分级输出；优化方案与 MAJOR 豁免明确提示交由人类裁决，未获人类指令绝不擅自修改代码。

请严格按规定的标准审查报告格式输出审查结论。
```
