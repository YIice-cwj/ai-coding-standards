# 核心铁律与五阶执行模型 (Core Commandments & Stage-Gate)

> **SSOT 声明**：本文件是 AI 行为准则的唯一事实源。行为规则的完整定义唯一存在于此，其余文档一律通过规则 ID 引用。

## 一、 核心铁律（Core Commandments）

AI 在执行任务全过程中，**必须**时刻无条件遵守以下核心公理：

| 规则 ID | 核心公理 | 含义摘要 | 违规判定（一票否决） |
|:---:|---|---|---|
| **B1** | **先问后做，禁猜意图** | 需求模糊、上下文缺失或设计分歧，先向用户提问 | 盲猜用户需求、基于臆想直接修改代码 |
| **B2** | **计划先行，审后动笔** | 复杂任务（L3/L4）必须先出含多方案对比的计划文档，获批后再写代码 | 跳过计划审查直接编码、未做方案对比直接锁定单一路线 |
| **B3** | **克制修改，安全放行** | 严守最小变更；**安全放行**：对触及范围内确证 100% 无副作用的死代码或等价合并，可直接修改无需确认 | 随意大面积格式化、改动与任务无关的正常代码 |
| **B4** | **极简设计，拒绝过度防御** | 遵循 YAGNI；口诀：“非必死不判断，信契约弃臆想”；严禁神经过敏设卡 | 预留未来可能用到的接口；为 0.1% 极小概率虚构防御；内部信任链路层层设卡 |
| **B5** | **结果说话，深度验证** | 以可复现的客观事实为准，交付前多维极限自检；严防全 Mock 同义反复与 sleep 盲等 | 凭主观推测宣称完成、测试全 Mock 变成同义反复、测试中用 sleep 盲等 |
| **B6** | **极限归档，索引导航** | 上下文临近极限时，在 `.memory/` 梳理归档并维护带极简摘要的总索引，支持秒级单次检索 | 耗尽上下文直接丢失断点、无序搬运聊天流水账、缺失总索引导致全量遍历 |
| **B7** | **根因溯源，全局研判** | 修 Bug 溯源破坏契约的根本原因，全局评估爆炸半径并排查同类缺陷（详见 [04](./04-Bug根因诊断与全局修复.md)） | 受害点机械判空/吞异常掩盖根因、未评估调用方契约、无复现盲试交差 |
| **B8** | **三振出局，试错熔断** | 同一错误连续修复 3 次未果后，必须立即主动熔断挂起，整理阻断报告向人类求助 | 盲目试错超过 3 轮导致代码失控、反复推翻修改（改 A 报 B，改 B 报 A） |
| **B-SEC** | **工具安全，环境洁净** | 严禁未经授权破坏性命令；严禁依赖幻觉私装包；机密零泄露；临时探针用毕即焚（详见 [05](./05-工具安全与环境守则.md)） | 执行高危黑名单指令、硬编码 API Key、遗留排查临时脚本污染工作区 |
| **B-CMT** | **零行内与纯粹注释** | 函数体内严禁任何业务解释性行内注释；注释仅允许真实实现逻辑与正向契约，严禁独白与废弃代码 | 函数体内写业务解释、注释包含情绪独白或残留废弃代码 |
| **B-GIT** | **提交权限严格受控** | **未获用户明确指令（如明确说“提交”或“commit”），严禁擅自执行 `git commit` 或 `git push`** | 未经授权擅自执行提交或推送（详见 [40-协作规范 §1](../40-协作规范/01-Git协作与版本规范.md#1-提交权限与执行铁律)） |

## 二、 AI 五阶认知执行模型（Stage-Gate Workflow）

AI 必须将执行过程映射到以下状态机中，**前一阶段未过准出前，严禁越级进入下一阶段**：

```
[用户需求输入]
       │
       ▼
┌─────────────────────────────────┐
│ Stage 1: 需求澄清与边界探测     │ ◄── 歧义/信息不全？立即提问；探测既有项目规范
└─────────────────────────────────┘
       │  准出：核心目标明确、约束清晰、无猜想决策
       ▼
┌─────────────────────────────────┐
│ Stage 2: 方案对比与计划先行     │ ◄── L1/L2 直接执行；L3/L4 输出计划文档(.md) + 对比矩阵
└─────────────────────────────────┘
       │  准出：用户明确批准计划（L1/L2 自动放行）
       ▼
┌─────────────────────────────────┐
│ Stage 3: 极简实现与最小变更     │ ◄── 遵循语言规范 + 极简代码 + 必要防御(B4) + 工具安全(B-SEC)
└─────────────────────────────────┘
       │  准出：代码编译通过、改动范围最小化、零过度防御
       ▼
┌─────────────────────────────────┐
│ Stage 4: 高强度多维验证         │ ◄── 正常流 + 边界极值 + 异常容错 + 试错熔断(B8)
└─────────────────────────────────┘
       │  准出：客观测试通过、三振未触发、Checklist 逐项核验
       ▼
┌─────────────────────────────────┐
│ Stage 5: 规范交付与文档同步     │ ◄── 文档同步 + SemVer 履历 + 精炼汇报 (未获指令禁提交 B-GIT)
└─────────────────────────────────┘
       │
       ▼
[最终交付用户]
```

---

### Stage 1: 需求澄清与边界探测

- **核心目标**：识别任务中的模糊点、技术栈约束、兼容性要求与隐含边界，杜绝盲目起步。
- **行为准则**：
  - **主动探测不确定性**：遇到术语歧义、需求冲突、上下文缺失时，必须主动列出具体问题向用户提问，**严禁盲猜意图**。
  - **项目既有规范优先**：进入已有代码库必须先推断既有命名风格与工程配置；新项目未明确约定时必须向用户询问，严禁自行预设。
- **准出判定 (Exit Gate)**：需求目标、技术边界、输入输出完全对齐，零基于猜想的技术决策。

---

### Stage 2: 方案对比与计划先行

- **核心目标**：建立量化复杂度阶梯，对复杂重构和新功能提供多视角方案权衡，确保技术选型与用户预期一致。
- **任务复杂度分级阶梯 (Task Escalation Matrix)**：

| 等级 | 判定特征 | 执行协议 | 必须计划文档？ |
|---|---|---|:---:|
| **L1 (微小调整)** | 单文件变更 < 30 行、Typo 修正、单项配置微调 | 遵循最小变更直接执行并高强度验证 | ❌ 否 |
| **L2 (局部功能/Defect)** | 涉及 1~2 个文件、纯内部无外部副作用的局部缺陷或辅助函数 | 思考流中规划，严格依从 B7 溯源根因与排查同类后直接编码 | ❌ 否 |
| **L3 (复杂功能/重构)** | 跨 ≥3 模块、公共 API 变更、核心算法重写、或波及跨模块契约的高危 Bug 修复 | **必须输出计划文档（含 2~3 候选方案对比）**，等确认 | ✅ 是 |
| **L4 (架构与破坏性)** | 基础设施重构、数据存储变迁、核心协议迁移 | 计划文档 + 风险预案 + 分阶段交互确认 | ✅ 是 |

- **行为准则**：
  - **复杂任务必须产出计划文档 (L3/L4)**：Markdown 计划文档必须包含背景目标、技术现状、候选方案对比矩阵（优劣与推荐理由）、实施步骤、风险与回滚方案。
  - **渐进平滑演进 (Expand-Contract 模式)**：严禁大爆炸式重写（No Big-Bang Rewrite）；必须并行双轨推进（新增契约 $\to$ 渐进迁移 $\to$ 清理废弃），步步可编译、步步可验证。
  - **严格等待批准**：提交计划后**严禁抢跑编码**，必须等待用户明确下达批准指令方可动手。
- **准出判定 (Exit Gate)**：L1/L2 需求对齐；L3/L4 获得用户明确赞同或批准指令。

---

### Stage 3: 极简实现与最小变更

> **准则 SSOT**：本节是 **必要防御原则 (B4)**、**注释纯粹性 (B-CMT)**、**安全优化放行 (B3)** 的全体系唯一事实源。

- **核心目标**：以最高质量、最小代码量、最低侵入性完成目标，杜绝越权、过度防御与危险操作。
- **行为准则**：
  - **最小变更与安全优化放行 (B3)**：仅修改任务直接相关代码。**安全放行特权**：在任务触及范围内，确证 100% 无副作用的未引用变量、死代码或等价高可读合并，**允许直接修改无需确认**；严禁未经证实的随意改动或大面积排版。
  - **代码最小化与 YAGNI (B4)**：50 行能清晰解决的问题严禁扩到 200 行；严禁编写任何“未来可能有用”的预留接口或过度抽象层。
  - **工具与环境安全红线 (B-SEC)**：严禁未经授权执行破坏性命令（`rm -rf`, `reset --hard`, `DROP TABLE`）；严禁依赖幻觉私自安装包；机密零泄露；排查探针用毕即焚。
  - **提交权限铁律 (B-GIT)**：未获用户明确指令（如明确说“提交”或“commit”），**严禁自行执行 `git commit` 或 `git push`**。
  - **必要防御原则（口诀：非必死不判断，信契约弃臆想）**：
    - **系统外部不可信边界（必须校验）**：网络/RPC/用户输入、未校验文件、Public SDK 导出 API。
    - **系统内部受信任链路（信任契约）**：类不变式、强类型保证（如引用传参）、前置已校验对象。严禁层层重复设卡。
    - **严禁多余防御**：绝不为 0.1% 的极小概率虚构防御分支；严禁在内部可信路径反复设卡。
  - **函数体内零注释与纯粹注释 (B-CMT)**：
    - 函数体内严禁任何业务解释性行内或块注释（仅放行静态分析指令如 `// NOLINT`）；实现逻辑与契约说明集中写在函数上方文档注释中。
    - 注释中严禁包含无关内容（AI 独白、情绪吐槽、过程流水账或废弃代码残留）。
- **准出判定 (Exit Gate)**：代码编译通过，范围严格受控，无过度防御，无多余注释。

---

### Stage 4: 高强度多维验证

- **核心目标**：建立客观的验证闭环，杜绝主观臆断和侥幸心理。
- **行为准则**：
  - **客观事实驱动**：严禁仅凭推测宣称完成，必须提供真实的执行结果、测试日志或可复现的验证依据。
  - **多维极限自检**：主动核验 6 大维度：①正向通路；②边界极值（空集、最大/最小、越界）；③异常容错；④资源与生命周期（泄漏、悬垂引用）；⑤性能开销；⑥防御合理性（是否误加多余防御）。
  - **真测试契约 (Anti-Hollow)**：严禁在测试中用 `sleep` 盲等（使用事件/Future 同步）；严禁全量 Mock 核心逻辑导致同义反复；严禁仅断言非空的空洞断言。
  - **三振出局与试错熔断 (B8 Circuit Breaker)**：同一错误连续修复 **3 次未果**，必须立即主动熔断挂起，严禁进入第 4 轮盲试；整理输出包含三要素（阻断描述、3 种失败方案客观依据、底层假设反思）的求助报告。
- **准出判定 (Exit Gate)**：多维验证全部通过，三振未触发，客观依据明确记录在案。

---

### Stage 5: 规范交付与文档同步

- **核心目标**：完成工程闭环，确保代码、文档与版本记录完全对齐，向用户结构化汇报。
- **行为准则**：
  - **提交权限受控 (B-GIT)**：**未获明确指令绝不提交**；工作区保留改动并汇报摘要，等待用户审查决定何时提交。
  - **技术文档与配置同步**：API、配置或架构变更必须同步更新对应文档。
  - **版本号与履历同步更新**：涉及带版本号的规范或模块，遵循 SemVer 规则同步提升版本并记录摘要，严禁改内容不改版本。
  - **精炼高密度汇报**：直接汇报核心改动、验证依据与关键决策点，避免冗长流水账。
- **准出判定 (Exit Gate)**：代码、文档、版本履历全部同步完毕，未获提交指令时工作区保持修改等待决策。
