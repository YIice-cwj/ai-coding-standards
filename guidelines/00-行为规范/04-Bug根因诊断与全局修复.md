## 一、 核心铁律：B7 根因溯源，全局研判

| 规则 ID | 核心公理 | 行为铁律（违规直接打回） |
|:---:|---|---|
| **B7** | **根因溯源，全局研判** | 修 Bug 严禁地表止痛式表面修补；必须向上溯源破坏业务契约的根本原因，从全局调用链评估爆炸半径并排查同类缺陷，产出根治性最优解与客观复现闭环依据。 |

### 核心四大原则
1. **现象 $\ne$ 根因**：崩溃、死锁、脏数据是“受害现场”，绝非元凶。
2. **严禁地表止痛**：绝不在报错点机械判空、赋假默认值或吞异常，严禁将显式故障隐式化（破坏快速失败）。
3. **全局研判优先**：必须核验所有调用方契约、并发安全与生命周期，杜绝局部修复引发级联崩溃。
4. **全景同类排查**：修一处，排查全库类似逻辑与镜像实现（Pattern Sweep），杜绝同类问题重复踩坑。

## 二、 四阶根治模型 (The 4-Phase Protocol)

AI 介入缺陷修复（Bug Fix / Defect）时，必须执行以下状态机：

```
[Bug 报告 / 崩溃现场]
       │
       ▼  Phase 1: 根因溯源 (Trace Root)
[拒绝地表止痛 · 5-Whys 逆推 · 锁定被破坏的不变式与契约]
       │
       ▼  Phase 2: 全局研判 (Blast Radius)
[上下游调用链测距 · 并发时序评估 · 全景同类缺陷排查 (Pattern Sweep)]
       │
       ▼  Phase 3: 最优方案权衡 (Clean Fix)
[方案矩阵对比：地表止痛(禁) vs 源头根治(荐) vs 契约重塑]
       │
       ▼  Phase 4: 闭环验证 (Proof of Cure)
[复现用例(Red) · 根除证明(Green) · 零回归验证]
       │
       ▼
[交付修复方案]
```

---

### Phase 1: 根因溯源 (Trace Root Cause)

- **区分受害现场与源头**：
  - 崩溃、空解引用、数组越界代码行往往只是受害者。
  - **严禁**在受害点机械添加 `if (!ptr) return;` 或空 `catch`；这会破坏快速失败（Fail-Fast），掩盖根因并使错误扩散至下游更难排查处。
- **5-Whys 逆推分析法**：顺着数据流与控制流向上逆推，锁定破坏业务不变式的源头：
  - *Why 1*：为何指针为空？（管理器传入了空实例）
  - *Why 2*：为何持空？（异步回调未正确注册该实例）
  - *Why 3*：为何未注册？（生命周期时序颠倒，清理在初始化前触发）
  - *Why 4*：为何时序颠倒？（状态机缺少状态流转守卫）
  - *Why 5*：**根因锁定**：状态机转移契约缺失，并发非法流转。
- **准出判定**：明确记录“最初在何处、因何种时序/逻辑违背了系统的业务不变式 (Invariant)”。

---

### Phase 2: 全局研判 (Global Blast Radius)

- **上下游拓扑与契约测距**：
  - **向上测距（Callers）**：排查所有调用方（尤其是 Public API 与覆盖函数），改动入参/返回值/异常是否打破调用方契约假设？
  - **向下测距（Dependencies）**：修正数据状态后，下游依赖该状态的计算模块是否会级联异常？
  - **旁路测距（Concurrency & Lifecycle）**：是否涉及共享资源竞态、跨线程访问或生命周期悬垂（GC / 智能指针引用计数）？
- **全景同类缺陷排查 (Pattern Sweep)**：
  - 检索项目中是否存在相同模式的逻辑、对称实现（Getter/Setter、序列化/反序列化、Save/Load）或同一基类的派生实现，整体纳入修复。
- **爆炸半径与任务定级**：
  - **低影响 (L2 局部级)**：纯内部私有逻辑，调用链封闭无外部副作用。
  - **高影响 (升级为 L3 级)**：触及公共 API、跨模块数据流、状态机变更。**必须立即触发 Stage 2 (B2 计划先行)**，输出候选方案对比文档等确认。
- **准出判定**：输出受影响模块清单、调用链路、潜在并发/时序风险及同类缺陷排查结果。

---

### Phase 3: 最优方案权衡 (Clean Fix)

#### 1. 方案对比决策矩阵

| 方案维度 | 方案 A：治标修补 (Band-Aid) | 方案 B：源头根治 (Root Cure) [推荐] | 方案 C：契约重塑 (Type/Architecture) |
|---|---|---|---|
| **改动位置** | 受害者现场（报错点） | 状态产生的源头 / 状态转移处 | 架构设计 / 强类型契约层 |
| **典型做法** | 加 `if (!ptr) return;` / 吞异常 | 修正状态生成、确保前置条件完备 | 引入强类型包装、RAII、不可变契约 |
| **根除程度** | ❌ 零（错误继续潜伏扩散） | ✅ 彻底根除非法状态 | ✅ 编译期/设计层面彻底杜绝 |
| **副作用风险** | 高（静默失败、下游死锁） | 低（遵循不变式恢复逻辑） | 中/高（改动较大，需充分审查） |
| **决策倾向** | **坚决打回禁止** | **默认首选执行** | 跨模块严重架构缺陷时升级评估 |

- **最优解标准**：①源头根治（非法状态无法生成）；②最小侵入（B3 & YAGNI）；③零过度防御（清理因怀疑该 Bug 留下的内部冗余防御）；④自说明性。
- **准出判定**：选定源头根治且侵入性最小的实施方案。

---

### Phase 4: 闭环验证 (Proof of Cure)

- **复现证明 (Reproduction Proof)**：修复前明确缺陷复现路径，编写最小失败用例（Red Test）或在思考流中给出清晰时序因果推导。
- **根除证明 (Proof of Cure)**：实施修复后，原复现用例稳定通过（Green Test），自证逻辑上不可能再产生该非法状态。
- **零回归验证 (Regression Guard)**：对 Phase 2 研判的所有调用方与关联路径执行回归测试；严禁在测试中用 `sleep` 盲等。
- **准出判定**：提供客观复现与根治验证通过的执行结果，形成完整证据闭环。

## 三、 典型正反模式对比 (Anti-Pattern vs. Best Practice)

```
【场景】：角色加载完成后，UI 面板从 PlayerState 获取 GuildInfo，在特定网络延迟下崩溃。
```

#### ❌ 反例：地表止痛（治标不治本）
```cpp
// 在 UI 受害现场就地判空：表面不崩，但公会名显示空白且永久卡死，下游按钮继续异常
void UGuildPanel::UpdateGuildName() {
    if (!MyPlayerState || !MyPlayerState->GuildInfo) { return; }
    GuildText->SetText(MyPlayerState->GuildInfo->GuildName);
}
```

#### ✅ 最佳实践：B7 根因溯源与源头根治
```cpp
// 1. 溯源：服务端网络同步包中 GuildInfo 与 PlayerState 复制时序存在竞态，UI 拉取过早
// 2. 全局研判：好友、战斗面板均存在类似偶发空白
// 3. 源头根治：确立网络到达契约 OnRep_GuildInfo，UI 监听委托，时序安全且根治
void AMyPlayerState::OnRep_GuildInfo() {
    OnGuildInfoReady.Broadcast(GuildInfo);
}
void UGuildPanel::NativeConstruct() {
    Super::NativeConstruct();
    GetPlayerState()->OnGuildInfoReady.AddDynamic(this, &UGuildPanel::OnGuildInfoReady);
}
```

## 四、 Bug 修复交付预检清单

- [ ] **1. 根因源头**：已定位产生非法状态的源头，而非仅在报错点加补丁。
- [ ] **2. 零地表掩盖**：杜绝机械判空、吞异常或虚假默认值。
- [ ] **3. 爆炸半径**：调用方与关联路径均已评估兼容性与时序契约。
- [ ] **4. 同类排查**：已检索并排查全库同类/对称模式漏洞 (Pattern Sweep)。
- [ ] **5. 证据闭环**：具备明确的复现证据、修复自证与零回归客观验证。
