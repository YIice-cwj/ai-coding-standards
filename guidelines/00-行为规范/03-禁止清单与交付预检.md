## 一、 AI 严厉禁止清单（Anti-Patterns）

以下行为构成对行为规范的严重违背，在任何情况下均属**绝对禁止事项（一票否决）**：

| 分类 | 严禁行为 | 典型错误表现 | 纠正要求 |
|---|---|---|---|
| **协作类** | **盲猜需求意图 (B1)** | 遇到模糊需求或缺失上下文不提问，凭猜想直接编码 | 存在任何疑问必须立即向用户澄清提问 |
| **协作类** | **未经审查直接编码 (B2)** | 面对 L3/L4 复杂任务跳过计划文档，直接改写业务代码 | 必须先产出含候选方案对比的计划文档并获批 |
| **协作类** | **擅自 Git 提交/推送 (B-GIT)** | 未获用户明确指令（“提交”/“commit”），自行执行 commit/push | 严格禁止擅自提交，工作区保留修改等待指令 |
| **协作类** | **大爆炸一次性重写 (B2)** | 复杂重构推倒重来，使系统长时间处于不可编译运行状态 | 必须采用展开-收缩模式 (Expand-Contract) 渐进推进 |
| **协作类** | **死循环盲目试错 (B8)** | 同一报错修复 3 次未果仍不主动熔断，继续盲改甚至引发次生灾难 | 严格遵循 B8 三振出局，主动挂起并结构化求助 |
| **协作类** | **上下文断层与无索引 (B6)** | 耗尽上下文直接截断，或无序堆叠流水账、全量遍历记忆文件 | 临近极限时在 `.memory/` 提炼归档，维护秒级总索引 |
| **质量类** | **地表止痛与管窥修补 (B7)** | 在受害现场机械判空/吞异常掩盖根因；修 Bug 不排查同类缺陷 | 溯源源头破坏的不变量，全局研判调用方并排查同类 |
| **质量类** | **无复现盲试与假测试 (B5)** | 仅凭“试一下看还崩不崩”交差；测试全 Mock 同义反复或 sleep 盲等 | 提供客观复现与根治闭环依据；断言具体业务值与状态 |
| **安全类** | **破坏性指令与幻觉依赖 (B-SEC)** | 未授权执行 `rm -rf` / 强推 / DROP；凭幻觉私自安装三方包 | 破坏性命令需确认；严禁私装依赖；Lockfile 锁定 |
| **安全类** | **机密泄露与环境污染 (B-SEC)** | 代码/日志明文包含 Key/Token；临时探针脚本遗留未清理 | 凭据绝对脱敏；探针脚本用毕即焚，保持工作区洁净 |
| **范围类** | **越权修改与过度设计 (B3/B4)** | 顺手修改无关代码；大面积格式化；编写“未来可能有用”的功能 | 严格克制最小变更（确证无害优化除外）；坚守 YAGNI |
| **设计类** | **神经过敏过度防御 (B4)** | 内部可信链路层层设卡；为 0.1% 极小概率虚构防御分支 | 口诀：“非必死不判断，信契约弃臆想”，主干保持直接 |
| **代码类** | **函数内业务注释与无关独白 (B-CMT)** | 函数体内写业务解释行内注释；注释写独白、吐槽或残留死代码 | 函数体内零业务注释；注释仅保留实现逻辑与正向契约 |
| **交付类** | **主观口头交付与版本漂移** | “写完了应该没问题”无客观依据；修改规范文件不升版本号 | 交付必须提供客观验证结果；修改规范必须遵循 SemVer 升级 |

## 二、 AI 交付前强制预检清单（Pre-Flight Checklist）

### 2.1 思考链（CoT）内省协议（Thinking Sandbox Protocol）
具备深度推理能力的大模型在生成代码或最终答复前，**必须在内部思考流末尾显式完成以下 3 项自问自答**：
1. **[计划对齐]**：本任务属于 L3/L4 任务吗？若是，是否已向用户提交过计划文档并已获明确批准？
2. **[变更边界]**：审视当前的 `git diff`，改动的每一行是否都严格属于当前任务或已确证的安全死代码/等价合并优化？是否存在任何未经授权的盲目重构或排版？
3. **[必要防御]**：主干逻辑是否像资深人类工程师一样直接？是否存在针对内部可信链路、类型系统或已保证数据的多余判断？是否存在针对 0.1% 极小概率的臆想设卡？

### 2.2 交付前逐项检查清单
AI 在向用户发出最终答复或交付代码前，**必须逐条核验**：

- [ ] **1. 计划与授权先行 (B1/B2)**：已澄清所有模糊点；L3/L4 复杂改动已提交计划文档并获用户批准；重构采用平滑演进模式。
- [ ] **2. 最小变更控制 (B3)**：`git diff` 中每一处修改均属当前任务或确证无副作用的安全死代码/等价合并；杜绝越权排版。
- [ ] **3. 极简实现与 YAGNI (B4)**：代码最小完备，零过度抽象；无任何预留未要求的功能接口。
- [ ] **4. 零过度防御与纯粹注释 (B4/B-CMT)**：“非必死不判断”，内部链路信任契约；函数体内零业务注释；注释无独白与死代码残留。
- [ ] **5. 语言规范依从性**：严格遵从目标语言或引擎的专有代码规范（如 C++ 15 层布局、UE5 命名与反射宏约束）。
- [ ] **6. 多维客观验证 (B5)**：提供客观测试输出或运行依据；杜绝全 Mock 同义反复与 sleep 盲等；断言精确覆盖具体业务值与异常。
- [ ] **7. 缺陷根治与全局闭环 (B7)**：若为 Bug 修复，已溯源根因，已完成上下游契约与同类缺陷排查，具备复现与根治证据闭环。
- [ ] **8. 试错熔断机制 (B8)**：若遇连续修复阻断，严格执行“同一问题失败 3 次立即熔断挂起求助”，杜绝盲目试错。
- [ ] **9. 工具与环境安全 (B-SEC)**：未执行破坏性黑名单命令；零新增未经验证三方依赖；零明文凭据泄露；临时探针脚本已清理。
- [ ] **10. 记忆归档与快速导航 (B6)**：触及上下文极限时，已在 `.memory/` 提炼归档并在总索引中同步极简摘要与直达链接。
- [ ] **11. 文档与版本同步 (SemVer)**：技术文档同步更新；规范文件修改已严格同步升级版本号与版本登记处。
- [ ] **12. 提交权限严格受控 (B-GIT)**：未获用户明确指令（“提交”/“commit”），绝对不擅自执行 `git commit` 或 `git push`。
