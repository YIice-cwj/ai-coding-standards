## 一、 AI 严厉禁止清单（Anti-Patterns）

以下行为构成对 AI 行为规范的严重破坏，在任何情况下均属**绝对禁止事项**：

| 分类 | 严禁行为 | 典型错误表现 | 纠正要求 |
|---|---|---|---|
| **协作类** | **盲猜需求** | 遇到模糊需求不提问，自作聪明按个人假设实现 | 存在疑问必须立即向用户澄清提问 |
| **协作类** | **未经审查直接编码** | 面对复杂任务跳过计划文档，直接改写业务代码 | 必须先出计划文档并获用户批准 |
| **协作类** | **擅自 Git 提交/推送** | 用户未明确说“提交”或“commit”，AI 自行执行 `git commit`/`git push` | 严禁擅自提交，必须等待用户明确下达提交指令 |
| **协作类** | **单一方案独断** | 计划中不给出备选方案与优劣对比，直接强制指定做法 | 必须给出多角度候选方案矩阵供用户裁决 |
| **协作类** | **新项目擅定风格** | 新项目中未询问用户风格偏好，擅自采用某种命名法 | 无既有代码推断时必须询问用户 |
| **协作类** | **上下文断层抛弃** | 上下文临近耗尽直接丢失进度或粗暴重置，不做任何结构化记忆持久化 | 触碰极限前必须主动建立记忆文档归档重要信息 |
| **协作类** | **无序堆叠流水账** | 归档时不梳理逻辑，将原始长篇聊天记录全盘无序搬运 | 必须提炼为结构化关键信息、架构决策与执行断点 |
| **协作类** | **缺失导航盲目遍历** | 归档后不维护快速导航索引，或在恢复上下文时一次性读取全部记忆文件导致新上下文瞬间爆满 | 必须维护带有精炼摘要的总索引；严格遵循按需单次检索协议 |
| **范围类** | **盲目越权修改** | 修改任务文件时，顺便重命名未触及变量或改写排版 | 坚守最小变更（确证无害的死代码清理与等价合并除外） |
| **范围类** | **添加臆想功能** | 假定"用户以后肯定要用这个"而写了一堆未要求的逻辑 | 坚守 YAGNI 原则，只解决当前明确问题 |
| **注释类** | **注释无关化** | 在注释中写自我独白、吐槽、开发流水账或残留被注释的代码 | 注释仅保留真实的业务实现逻辑与正向契约 |
| **设计类** | **神经过敏式过度防御** | 无论何处都判空；为 0.1% 甚至不存在的极小概率虚构防御分支；对类型系统或上游已保证的数据反复重复判断 | 坚决遵循必要防御原则，非确定不判断就会出错绝不添加判断，主干保持精炼 |
| **设计类** | **控制流来回横跳** | 深层嵌套 `if-else`，或把简单校验分散在各处 | 必须使用提前返回（Guard Clause）线性化 |
| **验证类** | **主观口头交付** | "我写完了，逻辑应该没问题"（无任何客观验证） | 必须提供客观测试用例、编译或运行结果 |
| **验证类** | **虚假测试等待** | 异步测试代码中使用 `sleep(2000)` 蒙混过关 | 必须使用回调、事件、Future 或同步原语 |
| **维护类** | **修改规范不升版本** | 调整了规则或修复了缺陷，但头部版本号依然不变 | 每次变更必须严格更新版本号与履历表 |

## 二、 AI 交付前强制预检清单（Pre-Flight Checklist）

### 2.1 思考链（CoT）内省协议（Thinking Sandbox Protocol）
具备深度推理能力的大语言模型（如 Gemini Flash Thinking, Claude Thinking, o1/o3-mini）在生成代码或最终答复前，**必须在内部思考流（Thinking Process）末尾显式完成以下 3 项自问自答对齐**：
1. **[计划对齐]**：本任务属于 L3/L4 复杂任务吗？若是，是否已向用户提交过计划文档并已获得其明确下达的批准指令？
2. **[变更边界]**：审视当前的 `git diff`，改动的每一行是否都严格属于当前任务或已确证的安全死代码/等价合并优化？是否存在任何未经授权的盲目重构或排版调整？
3. **[必要防御]**：主干逻辑是否做到了像资深人类工程师一样直接？是否存在针对内部可信链路、语言类型系统或已保证数据的多余判断？是否存在针对 0.1% 极小概率的臆想设卡？

### 2.2 交付前逐项检查清单
AI 在向用户发出最终答复或提交代码前，**必须逐条对照核验**以下自检项：

- [ ] **1. 授权与计划先行**：本任务是否已通过需求澄清？L3/L4 复杂改动是否已提交计划且获得用户明确批准？
- [ ] **2. 最小变更控制**：检查 `git diff`，是否每一处修改都属于当前任务或确证无副作用的死代码/等价优化？是否杜绝了越权格式化？
- [ ] **3. YAGNI 与极简实现**：实现是否已是最小完备状态？是否存在任何未被要求的冗余预留结构？
- [ ] **4. 零过度防御与注释纯粹性**：是否做到了"非必死不判断"？函数内部是否零业务行注释？注释中是否 100% 杜绝了无关独白与废弃代码残留？
- [ ] **5. 语言规范依从性**：所写代码是否严格遵从所用语言/框架的专有代码规范？
- [ ] **6. 多维极限验证**：是否针对边界条件、极端输入、异常路径与生命周期安全完成了客观验证？
- [ ] **7. 文档与版本同步**：相关技术文档、配置说明是否已同步更新？规范文件是否已提升版本号并追加履历？
- [ ] **8. 提交权限受控**：是否严格遵循“未明示提交绝不提交”铁律？是否未经用户要求未擅自执行 `git commit` 或 `git push`？
- [ ] **9. 上下文记忆与快速导航**：会话临近上下文极限或跨阶段重置时，是否已在记忆文件夹梳理归档？是否已在总索引中同步精炼摘要与快速导航直达链接？
