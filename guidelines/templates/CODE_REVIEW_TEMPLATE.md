# 📋 代码审查报告 (Code Review Summary)

> **审查基准**：[50-代码审查规范](../50-审查规范/01-代码审查规范.md)  
> **审查对象**：PR / MR / Commit `[Git Hash / 分支名]`  
> **审查执行流**：先查Bug缺陷 ➔ 查规范遵循 ➔ 查优化空间出方案 ➔ 回归审查出完工 ➔ 提交人工裁决

---

## 1. 评审总判定 (Review Verdict)

- **综合结论**: `[ PASS (准予合并) | NEEDS_WORK (需整改) | REJECT (严重阻断打回) ]`
- **问题分级**: `BLOCKER [n] / MAJOR [n] / MINOR [n] / NIT [n]`
- **审查概要**: 一两句话高度浓缩本次提交的代码质量评语、主干合规状态及主要结论。

---

## 2. Step 1: 真实 Bug 与业务缺陷排查 (Defect & Logic Scan)

> **判定红线**：仅核查影响功能正确性、并发安全、内存生命周期与资源泄露的真实缺陷。**基本不可能出现的极端条件（0.1% 极小概率）不计为缺陷**，内部受信任契约信任放行。

### 🔴 [BLOCKER] 严重业务缺陷与逻辑错误
- **文件与位置**: `path/to/file.cc:42`
- **缺陷性质**: `[功能逻辑断裂 | 状态损坏 | 并发竞态/死锁 | 内存泄漏/悬垂引用 | 未处理异常]`
- **问题说明**: 详细描述破坏了哪一项不变式或业务契约。
- **修复方案**:
  ```diff
  - [错误代码]
  + [修复代码]
  ```

*(若经排查无真实 Bug，标注：`✅ 未发现真实业务缺陷与逻辑漏洞`)*

---

## 3. Step 2: 规范合规核验矩阵 (Standards Compliance Matrix)

> 判定状态：`PASS / BLOCKER / MAJOR / MINOR / NIT`；BLOCKER 必须修复，MAJOR 需修复或由人类书面豁免并登记技术债。

| 核验维度 | 判定状态 | 违规说明与整改建议 |
|---|:---:|---|
| **过度防御 (B4)** | `PASS / BLOCKER` | 是否存在内部可信链路层层设卡、为 0.1% 概率设卡或 `&ref == nullptr` |
| **注释纯粹与同步 (B-CMT)** | `PASS / BLOCKER` | 函数体内零业务注释；函数文档头为语言原生多行格式（C++/UE5 为分标签 Doxygen，Python 为 Docstring，TS 为 JSDoc；严禁单行压缩）；**改动代码后文档头已 100% 同步对齐最新实现** |
| **真实测试与 95% 覆盖率 (B5)** | `PASS / BLOCKER` | 核心业务模块行覆盖率与分支覆盖率**必须 $\ge 95\%$**（豁免须人工审批）；零空跑无断言、空洞断言、吞异常、核心逻辑全量 Mock 同义反复等**滥竽充数测试**；测试零 sleep 盲等 |
| **职责边界与单文件单类** | `PASS / BLOCKER` | 一文件一类（纯类型聚合头除外）；UI 仅展示与分发意图，严禁直接改业务数据或持久化（R-ARCH-CLASS） |
| **变更边界与纯洁性 (B3)** | `PASS / BLOCKER` | 是否严格局限在任务必要范围，无越权排版与格式污染（死代码清理放行） |
| **缺陷根治与同类排查 (B7)** | `PASS / BLOCKER` | 是否溯源破坏不变式根因，完成三向测距与全景同类排查 (Pattern Sweep) |
| **语言与引擎专有陷阱** | `PASS / BLOCKER` | C++ 15 层类排布与防破坏 NRVO / UE5 UPROPERTY GC 保护与命名法 |
| **工具与凭据安全 (B-SEC)** | `PASS / BLOCKER` | 绝对杜绝明文 Key/Token 泄露，依赖锁定，临时排查探针用毕即焚 |
| **应用安全 (R-SEC-*)** | `PASS / BLOCKER` | 认证授权/输入输出/CSRF/SSRF/加密/反序列化/限流；详见 [10/08 应用安全](../10-通用代码规范/08-应用安全规范.md) |
| **性能与资源** | `PASS / MAJOR` | 可证实 N+1/热路径/无界内存；性能结论须有 profile/benchmark 证据（命令/环境/基线/统计量） |
| **依赖与供应链** | `PASS / BLOCKER` | 新增依赖必要性、Lockfile、CVE、许可证与 SBOM 审核 |
| **认知负荷控制与 SLAP** | `PASS / MAJOR` | 缩进深度 $\le 3$，长条件解构为具名意图常量，遵循单一抽象层次 |
| **接口幂等/窄事务/隐私** | `PASS / MAJOR` | 核心写接口幂等键、局部毫秒级窄事务、PII 个人隐私掩码脱敏 |

## 4. Step 3: 代码优化建议方案 (Optimization Proposal - 待人工审查裁决)

> **优化铁律**：**先实现，后优化**。必须在基线代码功能正确并通过测试后方可提出优化；提出的优化方案**必须保证业务行为与测试结果与原实现 100% 绝对一致（Zero Regression）**。
>
> **性能结论必须有证据**：涉及性能优化的结论必须附 profile/benchmark 或可复现度量，禁止凭感觉优化。

- **是否存在优化空间**: `[ 是 / 否 ]`
- **优化维度**: `[ 算法时间复杂度 | 内存分配/缓存局部性 | 认知复杂度与可读性 | SLAP 分层解耦 ]`
- **现状分析与优化理由**: 解释当前实现存在的优化空间及收益。
- **推荐最优方案与 Diff 预览**:
  ```diff
  - [当前基线实现]
  + [最优优化方案]
  ```
- **等价性与安全性保证**: 说明为何该方案能 100% 保证业务结果、外部接口契约与测试输出完全一致。
- **⚠️ 人工裁决提示**: 本优化方案已形成，**必须由人工审查决定是否采纳并执行**；未获人类明确指令前，AI 严禁擅自实施。

---

## 5. Step 4 & 5: 回归审查、完工判定与门禁 (Regression & Sign-Off)

- **回归验证核验**:
  - [ ] 若本轮有 Bug 修复或改动，已验证无任何副作用退化（Zero Side-effects）。
  - [ ] 自动化测试全量通过，核心业务行/分支覆盖率保持 $\ge 95\%$（豁免须人工审批）且断言真实有效。
  - [ ] 被触及函数的文档头注释已同步更新完毕。
- **完工判定**: `[ 技术审查完成，等待人工决策 / 阻断待整改 ]`
- **下一步行动**:
  - 若有优化方案，等待人类审查后下达“采纳优化”或“直接合入”指令；
  - 未获用户明确“提交/commit”指令前，严格遵循 `B-GIT`，工作区保持修改，不擅自执行提交。
