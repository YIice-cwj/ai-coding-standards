## 1. 核心安全红线对照表

| 规则标识 | 约束级别 | 强制行为 (DO) | 严禁行为 (DON'T / 一票打回) |
|---|:---:|---|---|
| **[R-SEC-AUTHN]** | MUST | 服务端强制认证；校验会话/Token 的签名、过期与撤销；Cookie 设置 `Secure`/`HttpOnly`/`SameSite` | 仅靠前端隐藏入口；信任客户端传入身份；明文传输凭据 |
| **[R-SEC-AUTHZ]** | MUST | 默认拒绝；每次访问校验对象级/租户级归属与权限；遵循最小权限 | 只校验登录态不校验资源归属（IDOR）；越权读写他人数据 |
| **[R-SEC-INPUT]** | MUST | 外部输入在边界做 allowlist 校验（类型/长度/范围/格式）；拒绝未知字段；SQL 参数化见 [10/06](./06-数据库与持久化演进规范.md) | 直接拼接或信任原始输入；用黑名单过滤代替 allowlist |
| **[R-SEC-OUTPUT]** | MUST | 按上下文编码（HTML/JS/URL/CSS）；富文本使用可信 sanitizer；设置 CSP | 原样输出用户输入；用 `eval` 执行不可信输入；未净化 HTML 直接渲染 |
| **[R-SEC-CSRF]** | MUST | 状态变更接口校验 CSRF Token 或 SameSite；写操作禁止使用 GET | GET 触发写操作；无防护的跨站表单 |
| **[R-SEC-SSRF]** | MUST | 出站 URL 使用协议/域名 allowlist；阻断私网、链路本地与云元数据地址 | 直接请求用户传入 URL；允许任意协议或无约束重定向 |
| **[R-SEC-CRYPTO]** | MUST | TLS 1.2+；使用经审计的密码库；CSPRNG；密码使用 Argon2id/bcrypt/scrypt；禁止自研加密 | 用 MD5/SHA1 做安全校验；硬编码密钥；自研加密算法 |
| **[R-SEC-DESER]** | MUST | 不可信数据禁止不安全反序列化；先 Schema 校验再构造强类型对象；禁用 `eval` 与不安全原生对象反序列化 | 直接反序列化外部输入；信任序列化对象中的类型与字段 |
| **[R-SEC-RATE]** | MUST | 登录/注册/支付等敏感接口限流、锁定与幂等；防自动化滥用 | 无限流；失败次数不记录；重试无幂等保护 |
| **[R-SEC-DEP]** | MUST | 依赖锁版本、漏洞扫描、许可证与 SBOM 审核；新增依赖需评审 | 引入未审计依赖；忽略已知 CVE；使用浮动版本 |

## 2. 模式对比与正反例 (❌ vs ✅)

### 2.1 对象级授权 [R-SEC-AUTHZ]
```cpp
// ❌ 反例：仅校验登录态，未校验资源归属（IDOR）
std::expected<void, order_error_t> delete_order(const request_t& req, order_repository_t& repo) {
    repo.remove(req.order_id());
    return {};
}

// ✅ 正例：服务端强制对象级授权，默认拒绝
std::expected<void, order_error_t> delete_order(const request_t& req, order_repository_t& repo) {
    const auto order = repo.find(req.order_id());
    if (!order || order->owner_id() != req.user_id()) {
        return std::unexpected(order_error_t::not_found);
    }
    repo.remove(order->id());
    return {};
}
```

### 2.2 SSRF 出站 allowlist [R-SEC-SSRF]
```cpp
// ❌ 反例：直接请求用户传入 URL
std::expected<http_response_t, fetch_error_t> fetch_remote(const std::string& user_url) {
    return http_client_.get(user_url);
}

// ✅ 正例：协议/域名 allowlist，并阻断私网与云元数据地址
std::expected<http_response_t, fetch_error_t> fetch_remote(const std::string& user_url) {
    const auto parsed = parse_url(user_url);
    if (!is_https(parsed) || !is_allowed_host(parsed.host)) {
        return std::unexpected(fetch_error_t::blocked_destination);
    }
    if (is_private_or_link_local(parsed.host) || is_cloud_metadata(parsed.host)) {
        return std::unexpected(fetch_error_t::blocked_destination);
    }
    return http_client_.get(user_url);
}
```

### 2.3 密码哈希与凭据 [R-SEC-CRYPTO / R-OBS-SEC]
```cpp
// ❌ 反例：明文存储或使用弱哈希
void save_password(user_t& user, const std::string& raw_password) {
    user.set_password_hash(raw_password);
}

// ✅ 正例：强哈希 + 由受信组件管理盐与密钥
void save_password(user_t& user, const std::string& raw_password) {
    user.set_password_hash(password_hasher_.hash(raw_password));
}
```

## 3. 威胁建模最小要求

涉及认证、支付、文件上传、外部 URL 请求、富文本或跨租户数据的功能，L3 计划中必须至少列出：

- **资产**：需要保护的数据、凭据、内部服务与用户隐私。
- **信任边界**：浏览器/客户端、网关、服务、数据库、第三方回调与消息队列。
- **入口点**：所有接受外部输入的 API、文件、Webhook、URL 参数与消息。
- **滥用场景**：越权、注入、重放、SSRF、文件包含、拒绝服务与数据外泄。

## 4. 安全自检清单

- [ ] 认证与授权在服务端强制执行，对象级/租户级归属校验无遗漏。
- [ ] 所有外部输入在边界做 allowlist 校验；输出按上下文编码。
- [ ] 状态变更接口具备 CSRF 防护；无 GET 写操作。
- [ ] 外部 URL 请求具备协议/域名 allowlist，私网与云元数据地址被阻断。
- [ ] 凭据来自密钥管理或环境变量，日志/错误响应零明文；密码使用强哈希。
- [ ] 不可信数据不进入不安全反序列化；不使用 `eval` 处理外部输入。
- [ ] 敏感接口具备限流、锁定与幂等保护。
- [ ] 依赖锁版本并通过漏洞扫描；新增依赖已完成许可证与供应链评审。
- [ ] 高风险功能已完成威胁建模，滥用场景已纳入测试或审查清单。
