## 1. 代码风格与格式化

### 1.1 惯例与缩进
- 遵循目标语言官方事实标准（PEP 8, gofmt, Google Java Style, ESLint Standard）。
- 优先遵循仓库既有格式约定，同一项目严禁混用 Tab 和空格缩进。
- 源码文件必须使用 UTF-8 无 BOM 编码，统一使用 LF（`\n`）换行符，严禁 CRLF。

### 1.2 注释规范与函数内部零注释
> **准则 SSOT**：函数体内零业务注释、注释纯粹性见 [行为规范 · Stage 3](../00-行为规范/01-核心铁律与五阶执行模型.md#stage-3-极简实现与最小变更)。

- 实现思路、关键算法与参数说明必须集中在函数上方的文档注释中（Python `"""docstring"""`、TS/Java `/** */`、Go `//`）。
- **唯一例外**：仅允许编译器/静态分析指令（`# type: ignore`、`// NOLINT`、`// eslint-disable-next-line`）。
- 函数内部需要解释性注释才能看懂时，说明违反单一职责，必须拆分为子函数。

**正例 (Python)**：
```python
def calc_score(user: UserData) -> int:
    """计算用户综合得分。思路：基础分 + 活跃度加成 - 违规扣分。"""
    bonus = user.active_days * BONUS_PER_DAY
    return user.base_score + bonus - user.violations * PENALTY
```

**反例 (Python)**：
```python
def calc_score(user: UserData) -> int:
    bonus = user.active_days * BONUS_PER_DAY  # 活跃天数加成（错！禁行内注释）
    return user.base_score + bonus - user.violations * PENALTY  # 错！废话注释
```

## 2. 命名与语义规范

> **项目优先原则**：进入已有项目先推断既有命名法（snake_case, camelCase, PascalCase）保持一致；新项目未明确约定时必须向用户询问。

- **语义自解释**：标识符具备直观业务与技术含义，禁止无意义单字母（循环索引 `i`/`j` 除外）或难以辨认的缩写。
- **常量标识**：常量具备清晰识别度（全大写加下划线：`MAX_RETRY_COUNT`）。
- **内部成员隔离**：缺乏原生访问控制的语言（如 Python），私有属性使用单下划线 `_` 前缀；禁止双下划线 `__`（避免名称重整损坏多态，底层语言中属保留字）。
