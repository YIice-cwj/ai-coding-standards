## 1. 代码风格与格式化统一

### 1.1 团队与语言官方惯例
- **必须**严格遵循目标语言官方或行业事实标准风格指南（如 Python PEP 8、Go gofmt、Java Google Java Style、TypeScript ESLint Standard）。
- **必须**优先遵循目标仓库既有的格式约定；同一项目内**严禁**混用 Tab 和空格缩进。

### 1.2 编码与换行
- 源码文件**必须**使用 UTF-8 无 BOM 编码。
- 源码文件**必须**使用 LF（`\n`）换行符，**严禁**在任何平台下使用 CRLF。

### 1.3 注释规范与函数内部零注释原则

> **准则定义（SSOT）**：函数体内零业务注释、注释纯粹性（禁止独白/吐槽/废弃代码残留）的完整准则见 [行为规范 · Stage 3](../00-行为规范/01-核心铁律与五阶执行模型.md#stage-3-极简实现与最小变更)。本节给出各语言**文档注释格式**的落地细则。

- 函数实现思路、关键步骤、核心算法与注意事项，**必须**集中写在函数定义上方的文档注释块中（如 Python `"""docstring"""`、TypeScript/Java `/** */`、Go `//` 文档注释）。
- **唯一例外**：允许且仅允许静态分析/编译器指令（如 `# type: ignore`、`// NOLINT`、`// eslint-disable-next-line`、`/* fallthrough */`）。
- 若函数内部过于复杂必须依赖解释性注释才能被看懂，说明严重违反单一职责，**必须直接拆分为更小粒度的子函数**。

**正例 (Python)**：
```python
def calc_score(user: UserData) -> int:
    """计算用户综合得分。

    实现思路：基础分 + 活跃度加成 - 违规扣分。
    """
    bonus = user.active_days * BONUS_PER_DAY
    return user.base_score + bonus - user.violations * PENALTY
```

**反例 (Python)**：
```python
def calc_score(user: UserData) -> int:
    bonus = user.active_days * BONUS_PER_DAY  # 计算活跃天数加成（错！禁止行内注释）
    return user.base_score + bonus - user.violations * PENALTY  # 返回得分（错！）
```

## 2. 命名与语义规范

> **项目优先原则**：进入已有代码库时，AI **必须**先推断既有命名的风格（蛇形 snake_case、小驼峰 camelCase、大驼峰 PascalCase），保持风格统一；新项目未明确约定时必须向用户询问。

### 2.1 语义直观性
- 变量、函数、类名**必须**具备直观的业务与技术语义，自解释其职责，**禁止**无意义的单个字母（循环索引 `i`/`j` 除外）或难以辨认的缩写。
- 常量**必须**具备清晰的视觉识别度（通常全大写加下划线：`MAX_RETRY_COUNT`）。

### 2.2 内部与私有成员隔离
- 对缺乏原生访问控制的语言（如 Python），私有属性/方法**必须**使用单下划线 `_` 前缀显式标明内部属性。
- **禁止**使用双下划线 `__` 前缀（在 C++ 等底层语言中属保留标识符；在 Python 中会触发 name mangling 破坏多态访问）。
