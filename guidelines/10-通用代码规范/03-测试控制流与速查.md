## 1. 真测试契约与 95% 覆盖率门禁 (Anti-Hollow Testing & 95% Coverage Gate)

### 1.1 95% 覆盖率硬性门禁 (Coverage Gate $\ge 95\%$)
- **全维度量化指标**：所有交付的核心业务模块、接口契约与关键组件，其**行覆盖率（Line Coverage）和分支覆盖率（Branch Coverage）均必须达到 95% 以上**，未达标一律视为不合格，严禁合入或宣称交付。
- **严禁掩耳盗铃**：严禁通过大面积标记覆盖率忽略注释（如 `// LCOV_EXCL_LINE`、`# pragma: no cover`）或扩大白名单豁免范围来人为虚抬覆盖率；仅脚手架自动生成的基础模板或特定底层平台硬件适配经人工审批后方可豁免。

### 1.2 严禁滥竽充数测试代码 (Zero Hollow / Sham Tests)
95% 的覆盖率必须是**真实有效、具有缺陷拦截能力的深度测试**，严禁任何形式“只刷行数、不验逻辑”的滥竽充数测试：

| 检查维度 | 强制标准 (DO) | 违规滥竽充数反模式 (DON'T / 一票打回) |
|---|---|---|
| **断言有效性** | 精确断言具体业务返回值、状态转移字段、边界极值与副作用 | **空跑无断言**：仅调用接口触发代码执行刷行数，零断言；**空洞断言**：仅写 `assert(true)`、`EXPECT_NE(ptr, nullptr)`（仅判指针非空却不校验任何数据内容） |
| **Mock 边界** | 仅用于不可控外部边界（网络 RPC、第三方 HTTP、物理时钟、文件 I/O） | **同义反复 Mock**：将待测核心计算规则、校验逻辑或状态转移全量 Mock，变成“自己测自己” |
| **异常分支测试** | 精确断言抛出异常的具体类型、错误码与可行动错误信息 | **吞异常假覆盖**：用 `try { ... } catch (...) {}` 将被测异常代码包裹吞掉，假装跑过异常分支而不做任何断言 |
| **路径与边界** | 覆盖主通路、极值边界（空集、最大/最小边界、越界、溢出）与并发争用 | **正向路径单调刷行**：用不同入参反复跑同一条简单正向流凑覆盖率，刻意避开易出错的复杂边界与异常路径 |
| **异步验证** | 使用事件监听、Promise/Future 状态通知、条件变量或虚拟时钟同步 | **sleep 盲等**：严禁在测试中硬编码 `sleep()` 盲等撞大运 |
| **类封装性** | 依据公开契约与对外可见副作用测试；或使用测试友元受控暴露 | **破坏封装**：仅为单测访问将类的 `private` 成员强行改为 `public` |

### 1.3 C++ 测试对比示例

```cpp
// ❌ 滥竽充数反例：虚假覆盖率（行覆盖率看似 100%，实际零拦截能力，一票打回！）
TEST(payment_service_test, sham_process_payment_test) {
    payment_service_t service;
    order_t order{.id = "ord_001", .amount_cents = 5000};
    wallet_t wallet{.balance_cents = 10000};

    // 1. 空跑刷行数：调用了函数，但零断言，完全不管扣款是否成功、余额是否正确
    service.process_user_payment(order, wallet);

    // 2. 空洞断言：只断言指针非空或永真，根本不校验业务数据
    EXPECT_TRUE(order.id == "ord_001"); // 毫无意义的自证断言

    // 3. 吞异常假装覆盖异常分支：代码抛了异常直接吞掉，假装测试通过
    try {
        order_t invalid_order{.id = "", .amount_cents = -100};
        service.process_user_payment(invalid_order, wallet);
    } catch (...) {
        // 错！直接吞异常，未断言异常具体类型、错误码与上下文
    }
}

// ✅ 高标准真测试正例：覆盖率 >= 95%，真实验证业务状态转移、边界极值与具体异常
TEST(payment_service_test, genuine_process_payment_full_coverage) {
    payment_service_t service;

    // 1. 正常通路深度验证：精确断言返回值、状态机转移与余额副作用
    {
        order_t order{.id = "ord_001", .amount_cents = 5000};
        wallet_t wallet{.balance_cents = 10000};

        const auto result = service.process_user_payment(order, wallet);
        ASSERT_TRUE(result.has_value());
        EXPECT_EQ(wallet.balance_cents(), 5000);
        EXPECT_EQ(order.status(), order_status_t::paid);
    }

    // 2. 边界极值验证：余额恰好等于扣款金额（压线临界点）
    {
        order_t order{.id = "ord_002", .amount_cents = 5000};
        wallet_t wallet{.balance_cents = 5000};

        const auto result = service.process_user_payment(order, wallet);
        ASSERT_TRUE(result.has_value());
        EXPECT_EQ(wallet.balance_cents(), 0);
    }

    // 3. 业务分支与容错验证：余额不足拒绝扣款，余额保持不变（强一致性）
    {
        order_t order{.id = "ord_003", .amount_cents = 8000};
        wallet_t wallet{.balance_cents = 3000};

        const auto result = service.process_user_payment(order, wallet);
        ASSERT_FALSE(result.has_value());
        EXPECT_EQ(result.error(), payment_error_t::insufficient_balance);
        EXPECT_EQ(wallet.balance_cents(), 3000); // 确证无误扣副作用
    }

    // 4. 异常分支精确断言：非法金额抛出明确异常类型与包含实体 ID 的错误信息
    {
        order_t invalid_order{.id = "ord_err", .amount_cents = -1};
        wallet_t wallet{.balance_cents = 1000};

        EXPECT_THROW({
            try {
                service.process_user_payment(invalid_order, wallet);
            } catch (const invalid_order_amount_error& e) {
                EXPECT_STREQ(e.order_id().c_str(), "ord_err");
                throw;
            }
        }, invalid_order_amount_error);
    }
}
```

## 2. 测试策略、确定性与覆盖工具链

### 2.1 测试金字塔与职责边界
| 层级 | 核心目标 | 约束 |
|---|---|---|
| **单元测试** | 业务规则、状态转移、边界极值 | 纯内存、确定性、毫秒级；禁止真实网络、真实时钟与真实文件系统 |
| **集成测试** | 模块契约、数据库/HTTP/消息边界 | 使用真实或容器化依赖；覆盖事务、序列化、迁移与失败回滚 |
| **端到端测试** | 关键用户旅程 | 仅覆盖少数核心链路；严禁用 E2E 替代单元测试 |
| **性能基准（非功能）** | 核心热路径、已声明预算项与历史回归路径 | 独立套件、Release 构建、专用 runner；不计覆盖率、不替代功能测试；口径见 §5 |

- 默认以单元测试为主，集成测试覆盖关键边界，E2E 只验证关键旅程。
- 测试必须可重复、可并行、相互隔离；共享可变状态与执行顺序依赖一票打回。

### 2.2 确定性测试与 Flaky 治理
- **禁止盲等**：禁止 `sleep`、真实网络、真实系统时钟与不可控随机数；使用假时钟、依赖注入、事件或条件变量同步。
- **Flaky 测试零容忍**：发现即隔离并定位根因，严禁无脑重试、放宽断言或直接删除测试。
- **测试数据隔离**：使用 Builder/Factory 构造测试数据，禁止依赖生产数据；用例结束必须清理临时资源。
- **断言纪律**：每个用例只验证一个行为；遵循 Arrange-Act-Assert；异常路径必须断言具体异常类型或错误码。

```cpp
// ✅ C++ 确定性测试：注入假时钟，零 sleep 盲等
TEST(order_timeout_test, expires_after_deadline) {
    fake_clock_t clock{};
    order_service_t service{clock};
    const auto order = service.create_order(order_request_t{.id = "ord_001"});

    clock.advance(std::chrono::seconds{60});

    const auto result = service.get_order("ord_001");
    ASSERT_TRUE(result.has_value());
    EXPECT_EQ(result->status(), order_status_t::expired);
}
```

### 2.3 契约与迁移测试
- 对外 API/消息契约变更，必须有消费者/提供者契约测试或 Schema 校验。
- 数据库迁移必须验证前进迁移、数据回填与回滚预案；关键迁移需在真实数据库上执行。
- 序列化/反序列化必须有 round-trip 测试，覆盖版本兼容与未知字段。

### 2.4 覆盖率工具矩阵
| 语言/引擎 | 推荐工具 | 分支覆盖 | 门禁命令示例 |
|---|---|---|---|
| **C++** | gcov/lcov、llvm-cov | 支持 | `ctest` + `llvm-cov show` / `lcov --branch-coverage` |
| **Python** | pytest-cov、coverage.py | 支持 | `pytest --cov=src --cov-branch --cov-fail-under=95` |
| **TS/JS** | Vitest、Jest (v8/istanbul) | 支持 | `vitest run --coverage` / `jest --coverage` |
| **UE5** | Unreal Automation + 平台覆盖率工具 | 视工具链 | `Automation RunTests` + 平台覆盖率报告 |
| **Go** | `go test -coverprofile` + `go tool cover` | 语句覆盖为主 | `go test ./... -coverprofile=coverage.out` |
| **Java** | JaCoCo | 支持 | `mvn test jacoco:report` |

- 覆盖率报告必须随 PR/交付物提供；禁止通过忽略注释或扩大白名单虚抬覆盖率，豁免规则见 §1.1。
- 覆盖率门禁必须在 CI 强制执行，禁止仅依赖本地手工运行。

### 2.5 CI 质量门禁
- 合并前至少执行：静态检查/类型检查、单元测试、集成测试、覆盖率门禁、应用安全检查（见 [10/08 应用安全](./08-应用安全规范.md)）。
- 性能回归默认在专用 runner 或 nightly 执行；共享 CI runner 只记录不阻断；禁止与功能测试同套混跑（口径见 §5.4）。
- 任一门禁失败即阻断合并；禁止“本地通过但 CI 未跑”的口头交付。
- 分支保护与提交权限遵循 [40/01 Git 协作](../40-协作规范/01-Git协作与版本规范.md)；审查流程遵循 [50/01 代码审查](../50-审查规范/01-代码审查规范.md)。

## 3. 控制流与防御原则

### 3.1 提前返回 (Guard Clause)
主逻辑保持线性一路向下，有效嵌套深度严禁超过 3 层：

```cpp
// ❌ 反例：多层右移嵌套
bool process_order(const order_t& order) {
    if (order.is_valid()) {
        if (!order.is_cancelled()) { return execute_payment(order); }
    }
    return false;
}

// ✅ 正例：Guard Clause 扁平化线性流
bool process_order(const order_t& order) {
    if (!order.is_valid() || order.is_cancelled()) { return false; }
    return execute_payment(order);
}
```

### 3.2 必要防御 vs 过度防御（口诀：非必死不判断，信契约弃臆想）

```cpp
// ❌ 反例：神经过敏过度防御（内部链路层层设卡）
bool process_user_payment(const order_t& order, wallet_t& wallet) {
    if (&order == nullptr || &wallet == nullptr) return false;    // 语法已保证引用有效
    if (order.total_amount() < 0) return false;                   // 构造已保证非负
    if (wallet.user_id() != order.user_id()) return false;        // 鉴权拦截器已保证
    if (wallet.balance() < order.total_amount()) return false;
    wallet.deduct(order.total_amount());
    return true;
}

// ✅ 正例：信任内部链路与前置契约，仅检查关键业务分支
bool process_user_payment(const order_t& order, wallet_t& wallet) {
    if (wallet.balance() < order.total_amount()) { return false; }
    wallet.deduct(order.total_amount());
    return true;
}
```

### 3.3 死代码与安全优化放行特权 (B3)
在任务触及范围内，**确证 100% 行为等价与零副作用的死代码清理、未引用变量删除或高可读合并，允许直接修改，无需用户事先确认**。

## 4. 高频自检矩阵
- [ ] 核心业务测试行与分支覆盖率达到 95% 以上（豁免须人工审批），且无任何空跑无断言、空洞断言、吞异常或同义反复 Mock 等滥竽充数测试。
- [ ] 核心测试覆盖正常流、边界极值（压线值/空集/溢出）与具体异常，零 `sleep` 盲等。
- [ ] 测试金字塔分层合理，单元测试为主，集成/E2E 覆盖关键边界与关键旅程。
- [ ] 无 Flaky 测试；测试数据隔离、可并行、可重复。
- [ ] 性能敏感路径或已声明预算项具备 §5.5 的合格证据（命令/环境/基线/统计量）；无基线时只记录并登记技术债。
- [ ] 基准测试独立于功能测试套件，未纳入覆盖率统计，未使用 Debug 构建或覆盖率插桩数据下结论。
- [ ] 函数嵌套深度 $\le 3$，主逻辑通过 Guard Clause 线性平铺。
- [ ] 内部链路充分信任类型系统与上游契约，零神经过敏判空。

## 5. 性能验证与基准测试 (Performance Verification & Benchmarking)

> **SSOT 声明**：性能目标分层、基准覆盖边界、环境稳定性、门禁策略与证据最小集的唯一事实源。各域工具与命令见 [20/07](../20-CPP规范/07-构建测试与性能规范.md)、[30/10](../30-UE5规范/10-资源加载序列化与性能规范.md)、[60/03](../60-Web前端规范/03-前端工程化测试与安全规范.md)、[70/02](../70-Python工程规范/02-并发工程与测试规范.md)。
> **与 §1 的边界**：本章与 95% 覆盖率门禁相互独立；基准不计入覆盖率，覆盖率也不替代基准。

**适用判定**：仅当对象属于“性能敏感路径”或“已声明预算项”时适用本章。性能敏感路径须满足以下之一：命中项目热路径清单；有历史性能事故或回归记录；承载已声明预算（包体、首屏、帧耗时、Draw Call、资源体积）。判据是**该路径变慢是否会造成可感知的业务或预算损失**。

### 5.1 三层指标模型（不可互相替代）

| 层级 | 典型对象 | 指标形态 | 阈值来源 | 运行位置 | 失败处理 |
|---|---|---|---|---|---|
| **T1 预算型** | 包体、首屏字节、贴图/音频体积、帧耗时、Draw Call | 绝对数值 | 项目预算文档或 ADR | 每次构建 | 阻断 |
| **T2 微基准型** | 核心算法、容器/对象池、序列化编解码、查询构建器 | 中位数与离散度（CV/stddev） | 相对基线 | 专用 runner / nightly | 复测后阻断或登记技术债 |
| **T3 服务/SLO 型** | API、数据库访问、端到端旅程 | P95/P99、吞吐、错误率、内存增长 | SLA/SLO 契约 | 压测环境 / 线上监控 | 告警或按契约阻断 |

- **统计量归位**：微基准以中位数与离散度判定，**严禁套用 P95/P99**；P95/P99 仅用于 T3 的端到端与服务级验收。

### 5.2 覆盖边界（窄覆盖原则）

| 必须覆盖 (DO) | 严禁覆盖 (DON'T) |
|---|---|
| 已发生性能回归或事故的路径，作为回归基准 | 为每个函数/每个类生成基准 |
| 核心算法与数据结构（排序/索引/查找、哈希、缓存淘汰） | 用组合爆炸覆盖“所有可覆盖场景” |
| 序列化/反序列化编解码与批量转换 | 把基准当正确性测试，替代业务断言 |
| 分配与对象池热点、零拷贝路径 | 非热路径、纯 getter、脚手架代码 |
| 已声明预算项（包体、首屏、帧、资源体积） | 第三方库自身性能（应采信上游数据或做选型评估） |
| 对外契约的吞吐/延迟前置小规模压测 | 用微基准替代 E2E/压测证明端到端性能 |

- **不计入覆盖率**：基准测试不参与行/分支覆盖率统计，也不受 §1 的 95% 门禁约束。

### 5.3 环境与稳定性

1. **构建一致**：与被测发布配置一致（Release/`-O2`、关闭 Sanitizer 与覆盖率插桩）；禁止用 Debug 数据下结论。
2. **机器一致**：同一物理机或同一容器规格；记录 CPU 型号、OS、编译器/运行时版本、完整构建参数与 commit SHA。
3. **预热**：至少 1 轮预热并丢弃，消除缓存、频率爬升与运行时预热污染。
4. **采样量**：固定迭代次数或固定最短采样时长；重复 $\ge 5$ 轮，报告中位数与离散度，不以单次均值下结论。
5. **输入稳定**：固定数据规模与随机种子；基准内禁止网络、磁盘 I/O 与不可控并发。
6. **隔离**：基准与功能测试分套运行；禁止并行启动多个基准进程抢占 CPU。

### 5.4 门禁策略

- **默认相对基线回归**：判定“相对上一基线的退化”，而非写死绝对耗时；绝对值阈值仅用于 T1 已声明预算项。
- **触发条件**：PR 命中 `perf-sensitive` 标记，或改动命中项目热路径清单；其余改动不要求跑基准。
- **执行位置**：专用 runner 或 nightly；共享 CI runner 只记录不阻断。
- **复测策略**：超阈值先自动复测 2 次，仍超才判定，避免噪声误杀。
- **默认阈值**：中位数回退 $\ge 10\%$ 判定退化，关键路径可经 ADR 收紧至 5%；阈值必须随基线版本登记。
- **首次无基线**：只记录数据并登记技术债，禁止用“无基线数据”宣称优化有效。

### 5.5 证据最小集

| 字段 | 要求 |
|---|---|
| 命令 | 可复现的完整执行命令 |
| 构建 | 构建类型、优化级别、Sanitizer/覆盖率是否关闭 |
| 环境 | CPU、内存、OS、编译器/运行时版本、commit SHA |
| 基线 | 对比的基线版本或基线文件路径 |
| 统计 | 重复轮次、中位数、离散度（CV/stddev） |
| 结论 | 是否超阈值、判定依据、是否已复测 |

### 5.6 反空洞基准（无效证据）

- **无基线对比**：只给单次运行数值，无法证明变快或变慢。
- **无环境信息**：缺少构建类型、机器与编译器上下文，数据不可复现。
- **单次结论**：未预热、未重复、无离散度，直接宣称优化有效。
